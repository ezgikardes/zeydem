# 006 · Continuous integration on GitHub Actions, one job per app

**Status:** Accepted

**Context:** Vercel deploys the frontend and Render deploys the backend straight from `main`, so
delivery is automatic. Checking is not: lint, the type check and the tests run only when someone
remembers to run them locally. A change that breaks a test can reach `main`, and from there the
live site. This is repo-wide setup that belongs to no single user outcome, so it is done outside a
Jira ticket, on purpose.

**Options:**
- **Keep running the checks by hand.** No setup, but the rule depends on memory.
- **A git hook on the developer's machine** (pre-push). Fast feedback, but it is local, easy to
  skip, and a pull request never shows its result.
- **A hosted CI service:** GitHub Actions, or a separate one (CircleCI, GitLab CI).

**Decision:** GitHub Actions, in `.github/workflows/ci.yml`. It runs on every push to `main` and
every pull request into `main`, with two jobs that run in parallel:

| Job | Runs in | Steps |
|---|---|---|
| `frontend` | `frontend/` | `npm ci` → `npm run lint` → `tsc --noEmit` → `npm test` |
| `backend` | `backend/` | `mvn -B verify` (compile, unit tests, ArchUnit layer rules, Spring tests) |

- The backend tests use a real PostgreSQL (`zeydem_test`), so the `backend` job starts one as a
  service container. Its password is a fixed throwaway value written in the workflow: the database
  lives only as long as the job, so it is not a secret.
- The Node version is written once, in `engines` in `frontend/package.json` (`26.x`, the version
  Vercel builds with). The workflow reads it from there.

**Why this option:**
- The code already lives on GitHub: no new account, no new place to look, and the result shows on
  the pull request next to the diff.
- Free for a public repository; the workflow is one YAML file in the repo, reviewed like code.
- Two jobs because the apps share nothing at build time: different languages, packages and
  caches. In parallel the wait is the slower job, not the sum, and a red mark says which side
  broke.

**Evidence:** `npm run lint`, `tsc --noEmit` and `npm test` (48 tests) pass locally. The test
profile (`application-test.yaml`) points at `localhost:5432/zeydem_test`, and `DB_PASSWORD` has no
default in `application.yaml`.

**Left out on purpose:**
- **Builds** (`npm run build`, the Docker image): Vercel and Render already build on deploy, and a
  failed build there keeps the old version live.
- **Deployment from CI:** the platforms already deploy from `main`.
- **Testcontainers or H2 for the tests:** the service container gives the same PostgreSQL the tests
  already use, without a new dependency.
- **A matrix of versions, coverage reports, caching beyond npm and Maven:** one shop, one
  production version of each runtime.

**Trade-off accepted:**
- A green check matters only if merging waits for it: `main` needs a branch protection rule that
  requires both jobs, set by hand in the GitHub settings.
- Every run starts cold: installing packages and starting PostgreSQL take a minute or two.
- Lint and type errors in the frontend show up after a push, not while typing.

**Revisit when:** the frontend build starts failing on Vercel for reasons the tests do not catch,
end-to-end tests arrive (they need both apps running together), or the free minutes run out.
